# ADR-0007: Audio Graph の最小の形と、スレッド間の値の受け渡し

- Status: Accepted
- Date: 2026-10-07
- Decider: 所長（Ink Inc.）

## Decision

Phase 1（マイク → Gain → MASTER → 出力）の Audio Graph の形と、音声スレッドと UI の間の値の受け渡し方を、次のとおりにする。
数値はすべて初期値で、#38（CLI で音を出す Issue）以降の実測で調整する。

### Graph の形

- Phase 1 はつなぎ方を固定する：`MicrophoneSource → GainNode(MIC) → MixerNode → GainNode(MASTER) → Sink`。
  型は Source / Node / Mixer / Sink の抽象のまま作る（ARCHITECTURE.md §6）。動的なつなぎ替えは後の Phase で行う
- 置き場所は `ink-core` のモジュール（例：`graph`）。ARCHITECTURE.md §31 の `ink-audio` crate は、必要になってから分ける
- 内部のサンプル形式は f32。MIC は mono、Mixer と MASTER は stereo（2ch）。Phase 2 の BGM（stereo）をそのまま足せる形にする
- MIC（mono）を Mixer（stereo）に入れるときは、L/R に同じ値をそのまま入れる（音量を下げない）
- 出力が 2ch より多いときは、1・2ch に L/R を書き、残りは無音にする。出力が 1ch のときは L/R の平均を書く
- 入力が 2ch 以上のとき、MIC は1ch目だけを使う。どのチャンネルを使うかの設定は後の Phase で行う
- **MIC の分岐点**：MicrophoneSource の出力（Gain の前の「生の MIC」）を、後で複数の行き先に分けられる形にする。
  Phase 1 の行き先は Gain だけ。STT・ボイストリガー用の分岐（ARCHITECTURE.md §11・§12）は、ここから別のリングバッファで取り出す
- Graph が使うバッファは、ストリームを開くときに先に確保する。cpal から想定より大きいブロックが来たら、確保した大きさに分けて処理する（コールバックの中でメモリを確保しない）

### スレッドとクロック

- **Graph を回すのは出力側のコールバック。** 入力側のコールバックは、サンプル形式を f32 に変換して1ch目を取り出し、リングバッファに入れるだけにする
- 入力と出力の間には、ロックを使わない1対1（SPSC）のリングバッファを置く。crate は `rtrb` を使う（追加は #38 で行う）。容量は 200ms 分で、ストリームを開くときに確保する
- **目標の量**：開始時に、リングバッファへ目標の量を溜めてから鳴らし始める。
  目標の量は「20ms」と「実際のコールバックの大きさ（入力・出力の大きい方）」の大きい方とする。20ms は下限の初期値で、#38 で実測して決める
- **underrun（空）**：足りない分は無音を出し、underrun を1回数える。その後は、目標の量が溜まるまで無音を出してから再開する（underrun が続かないように）
- **overrun（溢れ）**：入力側のクロックが速いことによるずれは、出力側で古いデータを捨てて吸収する。
  溜まっている量が「目標の量 + 余裕」を超えたら、古いものから捨てて目標の量まで戻し、overrun を1回数える。
  余裕は「20ms」と「実際のコールバックの大きさ（入力・出力の大きい方）」の大きい方とする
- リングバッファが満杯で入力側が書けないときは、新しいデータを捨てて overrun を数える（最後の安全策。SPSC では書き込む側が古いデータを捨てられないため）
- underrun / overrun の回数は `AtomicU64` で数える（ARCHITECTURE.md §38 の XRuns に使う）
- **cpal のバッファサイズ**：Phase 1 は既定（`BufferSize::Default`）のまま使い、実際のコールバックの大きさを記録する。
  既定が大きすぎる（20ms を超える）環境があれば、#38 で `Fixed` にするかを決める（デバイスが対応する範囲の中で）
- **サンプルレート**：入力・出力の両方が 48kHz に対応していれば 48kHz で開く。だめなら共通のレートを探し、それも無ければエラーにする。リサンプルは Phase 4

### 遅延の測り方

- 比べるための数値は「推定の遅延」とする：入力のコールバックの大きさ + リングバッファに溜まっている量の平均 + 出力のコールバックの大きさ（ms に直す）
- #38 の PR に記録する値：サンプルレート、入力・出力のコールバックの大きさ（frames）、目標の量、溜まっている量の平均、推定の遅延（ms）、CPU 使用率、underrun / overrun の回数
- 実際の音の遅延（出力を入力に戻して録音で比べる、など）は、できる環境でだけ参考として測る

### 値の受け渡し

- **UI → 音声スレッド**：MIC の gain・mute、master volume は atomic で渡す（f32 のビット列を `AtomicU32` に入れる）。
  開始・停止やデバイスの変更は音声スレッドへ送らず、制御側でストリームを作り直す。そのため、Phase 1 ではコマンドのキューを使わない
- **gain の単位**：UI と設定では dB。音声スレッドには、制御側で倍率に直した値を渡す
  - 範囲：MIC gain は −60〜+24 dB、master volume は −60〜+6 dB。−60 dB は無音として扱う
  - 初期値：MIC gain・master volume とも 0 dB
- **スムージング**：gain が変わったら、10ms かけて目標の倍率まで直線で近づける（サンプルレートからサンプル数を計算する）。
  ミュートは「目標の倍率を 0 にする」として同じ近づけ方を使う（ジッパーノイズ・プチ音の対策）
- **メーター**：
  - 音声スレッドは、前回読まれてから一番大きい値（サンプルの絶対値のピーク、倍率）を保持する
  - ブロックの中の最大値は普通の変数で計算し、`AtomicU32::fetch_max` はブロックの終わりに1回だけ呼ぶ。0 以上の f32 はビット列の大小と値の大小が一致するので、ビット列のまま比べられる
  - NaN のサンプルは 0 として扱う（NaN のビット列は無限大より大きく、メーターが最大に張り付くため）
  - UI は読むときに 0 に戻す（`swap(0)`）
  - ピークを保持して少しずつ下げる表示と、dB への変換は UI 側で行う
  - MIC のメーターは gain の後・ミュートの前の値、MASTER のメーターは最終的な出力の値とする

## Context

Phase 1 の目標は「マイク → Gain → MASTER → 出力」（ARCHITECTURE.md §33）。実装（#34〜#42）を始める前に、Graph の形と、音声スレッドと UI の間の値の受け渡し方を決めておく必要がある。

- 音声のコールバックでは、ブロッキング・メモリ確保・ログ出力をしてはいけない（AGENTS.md §5、ARCHITECTURE.md §25）
- cpal（ADR-0002）では、入力と出力のコールバックが別々のスレッドで、別々のタイミングで呼ばれる。入力と出力が別のデバイスなら、クロックも別になる
- `ink-core` は cpal に依存しない（ADR-0003）
- Phase 2 で BGM・SE、Phase 5・6 で STT・ボイストリガーを足す（ROADMAP「公開とお披露目の計画」）。Phase 1 の形がそれを妨げないようにする

## Options

1. **出力側のコールバックで Graph を回し、入力とは SPSC のリングバッファでつなぐ。パラメータとメーターは atomic**
2. 入力側のコールバックで Graph を回し、出力へリングバッファで渡す
3. パラメータを Mutex で渡す
4. リングバッファの crate に `ringbuf` を使う

## Chosen

Option 1（リングバッファは `rtrb`）

## Why

- 出力側で回すと、出力が必要とする量をそのタイミングで作れる。Phase 2 の BGM・SE も、入力が無いときでも出力側で鳴らせる
- atomic とロックを使わないリングバッファなら、音声スレッドが待つことも、メモリを確保することもない
- `rtrb` 0.4.0 は MIT OR Apache-2.0 で、GPL-3.0 と組み合わせられる（ADR-0005）。実行時の依存が無く、リアルタイムの音声処理に使う前提で作られている
- MIC は1ch目だけを使う：USB オーディオでは、マイクが1ch目だけに入ることが多い。左右の平均にすると、そのとき 6dB 下がる

採用しなかった案:

- 入力側で Graph を回す：出力のタイミングとずれ、入力が無いと出力も止まる。underrun の扱いが複雑になる
- Mutex で渡す：音声スレッドが UI のロックを待つ可能性がある（AGENTS.md §5）
- `ringbuf` 0.5.2（MIT OR Apache-2.0）：機能は足りるが、実行時の依存（`crossbeam-utils`）が1つ多い

## Consequences

- **クロックのずれによる小さな途切れ（既知の制限）**：入力と出力が別のデバイスだと、数分に1回程度、古いデータを捨てる、または無音を出すことによる小さな途切れが起きる。これは Phase 1 の正常な動作とする
  - 例：100ppm のずれでは、20ms の余裕を約3分で使い切る
  - 同じデバイスの入出力（USB ヘッドセットなど）では、クロックが同じなので起きにくい
  - 解消は、クロックのずれに合わせたリサンプル（Phase 4）で行う
- 遅延は「入力のブロック + 目標の量 + 出力のブロック」以上になる。目標の量（20ms）は #38 で実測して決める
- ARCHITECTURE.md §25 は「具体方式は実装時にベンチマークして決定する」としている。この ADR は最初の方式を決めるもので、#38 で遅延・CPU・XRuns を測って確かめる。問題があれば ADR を改める
- Graph のつなぎ方は固定なので、Phase 2 で BGM・SE を足すときに Mixer の入力を増やす。動的なつなぎ替えが必要になったら、別の ADR で決める
- STT・ボイストリガー用の MIC の分岐は、Gain の前から取り出す。この ADR では分岐の口だけを用意し、取り出し方は Phase 5・6 で決める
- 入力が 2ch 以上でマイクが2ch目にある環境では、Phase 1 では音が入らない。チャンネルを選ぶ設定は後の Phase で行う
- Phase 1 ではコマンドのキューを使わない。音声スレッドへ値以外を送る必要が出たら（Phase 2 の SE の再生など）、そのときに決める
- `rtrb` は #38 で追加する。追加するときに、crate 名・バージョン・ライセンスを改めて提示する
