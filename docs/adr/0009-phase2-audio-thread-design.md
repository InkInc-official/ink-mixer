# ADR-0009: Phase 2（BGM・SE）の音声スレッドの作りと、音源のデコード

- Status: Accepted
- Date: 2026-10-15
- Decider: 所長（Ink Inc.）

## Decision

Phase 2 で BGM と SE を足すときの、音声スレッドの作りと、音源を読む部品の置き場所・使う crate を、次のとおりにする。
数値は初期値で、Phase 2 の各 Issue（#62・#63）の実測で調整する。

ADR-0007 の「音声スレッドへ値以外を送る必要が出たら（Phase 2 の SE の再生など）、そのときに決める」は、この ADR で決める。

> 2026-10-19 に、#62（D）の実装で SE まわりの細部を変更した（コマンドの形、置き場の場所、ボイスの数、戻りキューの容量）。
> 同じ日に、#63（E）の実装で BGM まわりの細部を変更した（リングの大きさ、`eof` の印、アンダランと始まり、Loop のつなぎ目、ワーカー、破棄順序、`run` の引数）。
> 変更した点と理由は末尾の「変更履歴」に書いた。該当する箇所には「（2026-10-19 変更）」と付けてある。

### 基本の原則

音声スレッドがやるのは、次の 3 つだけにする。

1. 事前に確保したバッファを読む・足す
2. `rtrb` のキューからコマンドを受け取る・戻りを送る
3. atomic を読み書きする

ファイルを読む、デコードする、リサンプルする、メモリを確保する・解放する、ログを出す、待つ、は音声スレッドでしない（AGENTS.md §5）。これらは制御スレッドかワーカースレッドで行う。

### 1. UI → 音声スレッドのコマンドキュー（SE 用）

- ロックを使わない 1 対 1（SPSC）の `rtrb`。読み手は音声スレッド（出力のコールバック）だけ
- **送り手は制御側の窓口 1 つに集約する。** UI と、将来の Event Engine の Action は、同じ入口（制御側の関数）を通る。複数のスレッドから呼ぶ場合は、制御側だけで `Mutex` を持つ（音声スレッドは待たない）
- コマンド（2026-10-19 変更）：`PlaySe { slot, sound, gain, policy }`（`sound` は `Arc<SoundData>`。鳴らす音を運ぶ）、`StopSe { slot }`、`StopAllSe`。**SE の置き場（slot）の表は音声側ではなく制御側（`SeController`）にある。** そのため `SetSe` / `ClearSe` のコマンドは無い（制御側の `set_sound` / `clear`）
- 音声スレッドは、1 ブロックの最初に、キューから**最大 64 個**まで取り出して処理する
- 容量は 256。満杯のとき、制御側は新しいコマンドを送らず（`QueueFull`）、数える（`commands_dropped`）。音声スレッドで数える必要はない（読み手は溢れさせない）
- BGM の Play / Pause / Stop / Loop は音声スレッドに送らない。ワーカーに送る（3.）。BGM のチャンネルの音量・ミュートは、MIC と同じ atomic（ADR-0007）
- SE のボイス（2026-10-19 変更）：**同時に鳴らせるのは 16、止めている最中（フェードアウト）の分として 16 を足し、物理的には 32**。事前に確保する。同じ SE をもう一度鳴らしたときの扱い（重ねる／止めて頭から／無視）は、`PlaySe` の `policy` で選ぶ
  - 鳴っているボイスが 16 のときの新しい再生は**捨てて数える**（`plays_dropped`）。鳴っているボイスを奪わない（奪うとプチ音が出る）。捨てた再生の `Arc` もすぐ返す
  - `Stop` / `StopAll` / `Restart` で、フェードアウトに 10 ms かける（プチ音を防ぐ）。フェード中のボイスは「同時に鳴らせる 16」に数えない
  - フェード中のボイスの枠（16）が埋まっているときにさらにフェードを始める場合は、**フェードの残りが一番少ない（一番古い）フェード中のボイスをその場で切り**、その `Arc` を返してから、新しいフェードを始める。ほぼ聞こえなくなっているボイスなので、切ったときの音の段差は最小で、物理ボイスが 32 で固定のまま、「鳴っているのが 16 未満なら空きボイスが必ずある」が崩れない

### 2. SE：デコード済みの音の持ち方と、`Arc` の解放

- SE は、ワーカー（制御側）で全部デコードし、出力のサンプルレートにリサンプルして、`Arc<SoundData>` で持つ。音声スレッドは再生位置を進めて読むだけ
- **`Arc` の最後の参照を音声スレッドで落とさない。** 落とすと、メモリの解放が音声スレッドで起きる。そのため、音声スレッドが持つ `Arc` は、手放すときに必ず**戻りキュー**（音声 → 制御の `rtrb`）へ送り、制御側で落とす
  - （2026-10-19 変更）音声スレッドが `Arc` を持つ場所は、鳴っているボイスと、コマンドキューの中の `PlaySe` だけ。`PlaySe` は `Arc` を運び、音声側は受け取った `Arc` を**必ず 1 回、戻りキューへ返す**。返すのは、再生が終わったとき・止められたとき（フェードの終わり、または切られたとき）、再生しなかったとき（捨てた・無視した・空の音）のいずれか
  - ストリームを閉じてプレイヤーが破棄されるとき（バックエンドのワーカースレッドで起きる）も、ボイスの `Arc` と、まだ処理されていないコマンドの `Arc` を戻りキューへ返す（`Drop`）。解放は制御側（`SeController` の `collect()`、または `SeController` の破棄）で起きる
- **戻りキューが音声スレッドで満杯にならないことを保証する：**
  - 戻りキューの容量（2026-10-19 変更）は、「**物理ボイスの数（32）+ コマンドキューの容量（256）= 288**」にする。これは**同時に鳴らせるボイスの数（16）以上**でもある。音声スレッドが同時に持てる `Arc` と、コマンドキューの中で運ばれている `Arc` を合わせた数が上限なので、戻りキューには必ず入る（置き場の `Arc` は制御側にあり、数に入らない）
  - 制御側は、「音声側へ渡した `Arc` の数 − 戻りキューから受け取って落とした数」（未返却の数）を数え、**未返却の数が戻りキューの容量（288）に達しているときは、`PlaySe` を送らず `Busy` を返す**（`plays_busy` に数える）。これで、満杯にならないことが、音声スレッドの動きに関係なく成り立つ
  - 制御側は、戻りキューを定期的に空にする（`play` が毎回行う。窓では毎フレーム、または SE の読み込みのとき）。`PlaySe` を送るたびに自分で空にするので、ふつうは `Busy` にならない
  - それでも送れなかった場合（上の保証が崩れたバグ）は、音声スレッドで**解放せず、`Arc` をそのまま手放さずに保持し続ける（リークさせる）**。リークの数を atomic で数え、テストでは 0 であることを確かめる。音声スレッドでメモリの解放が起きるより、少量のリークとして見つけるほうがよい
- SE 1 本の長さは **60 秒まで**（f32 のステレオ・48kHz で約 23 MB）、SE 全部の合計は **256 MB まで**（約 11 分）。超えたときは、取り込みや読み込みの時点で断る（BGM に登録するよう案内する）。仮の数字で、E・F の実機で変えてよい
  - （2026-10-19 追記）合計は、置き場（`SeController`）に置いてある音の `memory_bytes()` の合計で数え、`set_sound` が上限（256 MiB）を超えるなら `TotalTooLarge` で断る（置き換えは、古い音を引いて新しい音を足して判断する）。出力レートと違う音は `RateMismatch`、空の音は `EmptySound` で断る
  - 鳴っている最中に置き換えた音は、ボイスが終わるまでメモリに残る。上限を一時的に超えうるが、1 本 60 秒以下 × 16 ボイスの範囲で収まる
  - 読み込み中の一時的なピーク（最終サイズの約 3.3 倍）は合計に数えない。そのかわり、**読み込みは 1 本ずつ順に行い、同時に何本も読まない**（`run --se` は 1 本）。最悪でも、合計の上限 256 MiB + 最大の 1 本のピーク（約 70 MB）≒ 330 MB
- **出力のサンプルレートが変わったとき**（#41 のセッションの作り直し）：元のデータは持たず、**ファイルから読み直す**（デコードとリサンプルをワーカーで）。測定では 3 秒の SE のデコードが 2〜4 ms、5 分の曲のデコード + リサンプルが約 0.8 秒で、60 秒の SE でも約 0.15 秒。読み込み中は、その SE を鳴らせない（画面に「読み込み中」を出す）

### 3. BGM：ストリーミング

- BGM は**ストリーミング**にする：ワーカースレッドが、ファイルを読む → デコード → 必要ならリサンプル → リングバッファに入れる。音声スレッドはリングバッファから読むだけ。**長さの上限は無い**（SE の 60 秒とは別）
  - 5 分のステレオ（f32）を全部持つと約 100〜110 MiB になる（測定）。RAM 8GB の創作PC で曲をいくつも持つのは避けたい。ストリーミングなら、メモリは数 MiB
- リングバッファは **1 秒分と「ブロックの 4 倍」の大きい方**（2026-10-19 変更。当初は 1 秒分）。製品のブロック（4096 フレーム）では、いつも 1 秒分になる：44.1 kHz で 44,100 フレーム ≒ 353 KB、48 kHz で 48,000 フレーム ≒ 384 KB、96 kHz で 96,000 フレーム ≒ 768 KB（左右の f32 で 1 フレーム 8 バイト）。ワーカーのスケジュールの遅れを吸収できる大きさで、足りなければ実機で広げる。小さなレートのテストでも、始まりの量にブロック 1 つが入るようにするため、下限を決めた
- **始まり（priming）**（2026-10-19 追加）：Play を受けても、リングバッファに **`max(100 ms, ブロック + フェード(10 ms))`** 分（48 kHz・4096 で 4,800 フレーム）が貯まるまでは無音を出す（44.1 kHz は 4,537、96 kHz は 9,600 フレーム）。そうしないと、始まってすぐに足りなくなる。曲の終わりの印（`eof`）が立っていれば、短い曲でも、貯まった分で始める
- 足りないとき（ワーカーが間に合わない）：**フェードアウト → 無音 → もう一度 priming** で戻る（2026-10-19 変更。当初は「無音を出して数える」だけ）。急に無音にするとプチ音が出るので、リングバッファに残った分（ブロック + フェード）でフェードアウトしてから無音にする。数えるのは、中断の回数（`underruns`）と、無音を出したフレーム数（`underrun_frames`）
- **Stop・曲の切り替え・シークで、リングバッファに残った音を捨てる手順**（ワーカーが書く側、音声スレッドが読む側なので、どちらも相手の側を触れない）：
  1. 制御側が「世代番号」（`AtomicU32`）を 1 つ進める。同時に再生を止める（フェードアウトの 10 ms が始まる）
  2. ワーカーは、世代が変わったことを見たら、古い音を書くのをやめ、**手元の chunk と書き込み位置を捨て**、`stopped = 世代` を書いて待つ
  3. 音声スレッドは、フェードアウトが終わり、`stopped = 現在の世代` になるまで**無音**を出す。そうなったら、リングバッファの中身を全部捨て（読み出し位置を進めるだけ。`rtrb` では O(1)）、`drained = 世代` を書く。このとき、再生位置と `finished` も戻す
  4. ワーカーは `drained = 世代` を見てから、**同じ曲を頭から**（または次の曲を）始める
  - 途中の間は無音になる。ワーカーが古い音を書くのと、音声スレッドが捨てるのが競合しない
  - **曲の終わりの印（`eof`）は世代の印つき**（2026-10-19 追加）：ワーカーは最後の書き込みの後に `eof = 世代 + 1` を書く。音声スレッドは、自分が追いついている世代 + 1 と等しいときだけ、終わりの印として扱う。Stop が続いたときに、古い曲の終わりの印が新しい曲に効かない
- Pause：音声スレッドが読むのをやめて無音を出す（リングバッファは残る）。始まりと終わりは、**サンプル単位の 10 ms の直線ランプ**（`GainNode`）で、プチ音を防ぐ（2026-10-19 変更。MIC と同じ 10 ms）。フェードアウトの間に読んだ分は、再開したときに飛ばされる（再生位置はその分進んでいる）
- 再生位置：音声スレッドが、読んだフレーム数を atomic で出す。UI が読む。曲の長さは、ワーカーが出力レートのフレーム数で伝える（ファイルが言う長さ。言わない MP3 は、1 周を読み終えた時点の実測）
- **Loop：** ワーカーが、ファイルの末尾で先頭へシークして続ける。音声スレッドは何も知らない。測定では、**MP3 にエンコーダーの gapless 情報（LAME / Xing タグ）があれば、symphonia が先頭・末尾の余分なフレームを取り除き、つなぎ目の隙間は 0**だった（symphonia のデコーダーの `gapless` は既定で有効。`rewind` の後も同じ長さと先頭になることを、テストで確かめた）。**タグが無い MP3 では、約 13〜20 ms の隙間が出る**（44.1kHz の 5 分で 591 フレーム ≒ 13.4 ms、48kHz の 3 秒で 943 フレーム ≒ 19.7 ms）。WAV は隙間が 0。
  - **1 周の出力フレーム数は、毎周同じ**（`round(総フレーム数 × 出力レート ÷ 元のレート)`）。リサンプラーの先頭の遅れが、周ごとに隙間にならない（2026-10-19 追加）
  - **つなぎ目の段差をならす**（2026-10-19 追加。案 B）：2 周目以降の先頭の 1.5 ms（48 kHz で 72 フレーム、44.1 kHz で 66 フレーム）に、前の周の最後の 2 フレームから外挿した値と新しい周の最初の値の差を、直線で 0 に戻しながら足す。曲の始まりと、Stop の後の始まりには掛けない。ワーカーだけの処理（リサンプラーの出力に掛ける）
  - 既知の制限として、**MP3 は、つなぎ目に小さな隙間が出ることがある**（エンコーダーによる）と書く。**ループさせたい曲は WAV を推奨**と案内する（README は #63 で書いた。UI の説明は F）
- **ワーカー**（2026-10-19 追加）：`ink-bgm` という名前のスレッドが 1 本。1 回に 2048 フレーム（`BGM_WRITE_CHUNK_FRAMES`）を書き、リングバッファが満杯なら 5 ms、することが無ければ 2 ms 寝る。終わるのは、`BgmWorker` が破棄されたときだけ（曲の終わりや失敗では終わらない）。曲を開けない、途中で読めなくなった、ループの 1 周が 0 フレームだった、のときは、ログを `debug!` で出し、プレイヤーには「空の曲が終わった」と伝え（`begin_stream(Some(0))` と `mark_eof`）、`BgmFailure` を記録する。ワーカーは続き、次の Stop で同じ曲を開き直す
- **破棄の順序**（2026-10-19 追加）：`Bgm`（コントローラーとワーカー）は、ワーカーを先に join し、コントローラーを後に落とす。`AudioSession` は `input`、`output`、`se`、`bgm` の順に落とす。`BgmPlayer` の `Drop` は、リングバッファの読み側をコントローラーの持つ入れ物に移す（確保も解放もしない）ので、リングバッファの解放は制御側のスレッドで起きる

### 4. リサンプル

- rubato の FFT 版（`Fft`、`FixedSync::Input`）。SE は読み込み時に一括、BGM はワーカーが 1024 フレームのチャンクごとに。元と出力が同じレートなら何もしない
  - （2026-10-19 追記）BGM のチャンク版（`ink-media` の `StreamResampler`）は、rubato の先頭の遅れ（最大 0.5 秒）を数えて取り除き、終わりを押し出して、曲全体に一括版を使った結果と**ビット単位で一致**する。メモリは通常のレートで 40〜140 KiB、公約数の小さいレート（44,101 → 48,000）で約 5 MiB、試した 99 のレートの最悪で約 13 MiB
- 測定（Intel N100）：44.1kHz → 48kHz の 5 分の曲で、一括 約 0.37〜0.38 秒（実時間の約 800 倍）。チャンクごと（BGM を再生しながら）では、実時間に対して CPU の約 0.1%（1 コア）、1 チャンクの最悪が約 0.1 ms。44.1kHz → 96kHz では約 0.2%、1 チャンクの最悪が約 4 ms。どれもワーカーでの処理で、音声スレッドには影響しない

### 5. 使う crate

- **symphonia 0.6.1**（MPL-2.0）：WAV / MP3 のデコード。`default-features = false`、`features = ["mp3", "wav", "pcm", "id3v2"]`。`symphonia-*` の各 crate（core / bundle-mp3 / codec-pcm / format-riff / metadata）も MPL-2.0。**改変せず依存として使う**（AGENTS.md §4 の 9）
  - 既定の features には `mp3` が入っていない。ogg・flac・vorbis・mkv などは使わないので入れない
  - 0.6 系は新しい。公式のドキュメントにも「API は変わりうる」とあるので、バージョンを固定して使う（`ink-media/Cargo.toml` は `=0.6.1`）
  - **新しい版に上げるときは、まず読み飛ばしのテストを確かめる。** `reader.rs` と `decode.rs` のテストは、`tone-44k-stereo-id3.mp3` のバイト位置 1367〜1370 を壊して「1 パケットが読み飛ばされる」ことを確かめている。どのパケットが読み飛ばされるかは版によって変わりうる
- **rubato 5.0.1**（MIT OR Apache-2.0）：サンプルレートの変換。既定の `fft_resampler`。バッファの受け渡しに使う `audioadapter-buffers`（MIT OR Apache-2.0）は、rubato が再エクスポートしている（`rubato::audioadapter_buffers`）ので、直接の依存にはしない
- 依存の全部（試作の依存木：33 の package）：6 つが MPL-2.0（symphonia の上の 6 つ）、そのほかは MIT / Apache-2.0 / Zlib / 0BSD の組み合わせ。ビルド時だけ使う `unicode-ident` は `(MIT OR Apache-2.0) AND Unicode-3.0`。GPL-3.0 と組み合わせられない種類はない。なお、**このリポジトリで新しく増える package は 22**（`Cargo.lock` が 373 から 396 になるうち、`ink-media` 自身を除く第三者のもの。`syn` などの残りは、すでにある）
- MPL-2.0 は、一般に GPL-3.0 と組み合わせられる（MPL-2.0 の Secondary License の条項）。配布するときは、MPL のファイルの通知と、ソースの入手方法を示す（Phase 2 の `cargo-about`、#66）。この ADR の判断は一般的な考え方に基づくもので、法的な助言ではない
- 採らない crate：`minimp3`（C のコードを含む）、`notify`（rc 版。フォルダの反映は更新ボタンで足りる）、`hound`（本体では不要。symphonia が WAV も読む）

### 6. デコーダーの置き場所：新しい crate `ink-media`

- **`ink-media`**（新しい crate）に、音源のデコードとリサンプルを置く。依存の向きは `ink-media → ink-core`（ADR-0003 と同じ、葉の crate が core に依存する向き）
- `ink-core` には、デコード後の音を表す素の型（`SoundData`：f32 のステレオ、サンプルレート）、Graph、コマンドキュー、Asset のモデルとライブラリ（コーデックを使わない）を置く。ファイルの情報（長さ・レート）は、アプリが `ink-media` で調べて `ink-core` に渡す
- `app/ink-mixer` に、ワーカー、窓、配線を置く
- ARCHITECTURE.md §31 の構成案に `ink-media` を足す。`ink-audio` / `ink-assets` は、これまでどおり必要になってから分ける

### 7. `ink-mixer run` の拡張（D・E で実装）

画面なしで CPU・xrun・underrun を測るため、`run` に次の引数を足す。音量は dB で、既定は 0 dB（全体は `--master` の既定 −12 dB が守る）。`--se` と `--bgm` は同時に指定できる。

| 引数 | 内容 |
|---|---|
| `--se <FILE>` | SE を一定の間隔でくり返し鳴らす（#62 で実装済み） |
| `--se-every <SECONDS>` | その間隔（既定 2。0 より大きい有限の数。`--se` が無いと指定できない） |
| `--se-volume <DB>` | SE の音量（`--se` が無いと指定できない） |
| `--bgm <FILE>` | BGM を再生する（WAV / MP3、長さの上限なし） |
| `--bgm-loop` | BGM を Loop する（`--bgm` が無いと指定できない） |
| `--bgm-volume <DB>` | BGM の音量（−60〜+6、範囲外はエラー。`--bgm` が無いと指定できない）（2026-10-19 変更） |
| `--bgm-cycle <SECONDS>` | **実機確認用の補助。** N 秒ごとに一時停止 → 1 秒後に再生、2 回に 1 回は停止 → 頭から再生をくり返す（1 より大きい。`--bgm` が無いと指定できない）（2026-10-19 追加） |

引数が無い `run` の出力は変えない。`--se` のときだけ、`se:` の行、メーターの `SE` の項目、summary の `SE:` の行（started / ignored / dropped / commands dropped / busy / leaked）が増える。`--bgm` のときだけ、`bgm:` の行（ファイル・長さ・レート・音量・Loop）、メーターの `BGM` の項目（MIC と SE の間）、1 秒ごとの `bgm:` の状態の行、summary の `BGM:` の行（underruns / min buffer / played / loops / skipped packets / finished / failures）が増える。BGM に `leaked` は無い（音声スレッドに `Arc` を渡さない）。曲の失敗は、標準エラーの `BGM stopped: …` の 1 行で知らせる（MIC と SE は続く）。

## Context

Phase 2 の目標は「MIC + BGM + SE を同時にミックスして出力できる」こと（ARCHITECTURE.md §33）。実装（#60〜#66）を始める前に、音声スレッドの作りを決める必要がある。

- 音声のコールバックでは、ブロッキング・メモリの確保と解放・ログ出力をしてはいけない（AGENTS.md §5、ARCHITECTURE.md §25）
- ADR-0007 は、Phase 1 では音声スレッドへ「値」（atomic）しか送らず、コマンドのキューを使わないとした。SE の再生は「値」では足りず、キューが要る
- SE は短く（数秒）、BGM は長い（数分）。扱いを分けると、メモリも CPU も小さくできる
- `ink-core` は `cpal` に依存しない（ADR-0003）。同じ考え方で、MPL-2.0 の symphonia を `ink-core` に入れたくない
- 創作PC は RAM 8GB で、ビルドも軽くしたい（AGENTS.md §2）

## 測定（試作）

試作は、リポジトリの外の小さな cargo プロジェクトで、symphonia 0.6.1 と rubato 5.0.1 を使って作った（コミットしない）。試験音源はすべて自作（`ffmpeg` / `lame` で作った正弦波）。環境：創作PC（Intel N100、4 コア）、release ビルド、1 つずつ別のプロセスで測った。

| 測ったもの | 結果 |
|---|---|
| 5 分のステレオを全部デコード：WAV（48kHz / 44.1kHz、16bit） | 約 145 ms（実時間の約 2000 倍）。f32 で 100〜109 MiB |
| 5 分のステレオを全部デコード：MP3（44.1kHz、192kbps、ID3 付き）、LAME / ffmpeg の 2 種 | 約 380〜400 ms（約 760〜790 倍）。f32 で 100 MiB。ID3v2 タグ付きでも読めた |
| 3 秒の SE をデコード | WAV 2 ms、MP3 4 ms。1〜2 MiB |
| ストリーミング（捨てながら）：WAV / MP3 の 5 分 | WAV は実時間の約 4000 倍（1 コアの約 0.02%）、MP3 は約 1000 倍（約 0.10%）。メモリは約 3 MiB |
| リサンプル：44.1kHz → 48kHz、5 分 | 一括 約 0.37〜0.38 秒。チャンク（1024 フレーム）ごとでは 1 コアの約 0.1%、最悪の 1 チャンクが約 0.1 ms |
| リサンプル：48kHz → 44.1kHz、44.1kHz → 96kHz | 約 0.1%、約 0.2%（最悪の 1 チャンクが約 4 ms） |
| シーク：先頭へ戻る / 5 分の中央へ | 先頭は 0.01〜0.02 ms。中央は MP3 で約 1 ms（要求より約 1300 フレーム手前に着く） |
| Loop のつなぎ目：WAV | 隙間 0 |

| 依存木（`mp3` `wav` `pcm` `id3v2` と rubato、ビルド時の依存を含む） | 33 package。MPL-2.0 が 6（symphonia の各 crate）、残りは MIT / Apache-2.0 / Zlib / 0BSD の組み合わせ |
| 依存の release ビルド（jobs = 2） | 約 19 秒 |

## Options

1. **SE は全部デコード、BGM はストリーミング。コマンドは `rtrb`。`Arc` は戻りキューで返す**
2. SE も BGM も全部デコードして持つ
3. SE も BGM もストリーミングにする
4. `Arc` を音声スレッドで落とす（ライブラリが最後まで持っていることを期待する）
5. コマンドを `Mutex` 付きのキューで渡す

デコーダーの置き場所：

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. 新しい crate `ink-media`** | デコードとリサンプルだけを持つ | symphonia（MPL-2.0 と多数の子 crate）と rubato を core に入れない。core のビルドとテストが軽いまま。MPL の依存が 1 か所に閉じる | crate が 1 つ増える |
| B. `ink-core` の module | 手軽 | crate が増えない | core が重くなり、`cpal` を外したのと同じ理由に反する |
| C. ARCHITECTURE.md §31 の `ink-assets` に入れる | デコードと Asset 管理を同じ crate に | §31 の構成案に沿う | 「ファイルの管理」と「コーデック」の責務が混ざる。Asset 管理には MPL の依存が要らない |

## Chosen

Option 1（SE は全部デコード、BGM はストリーミング、コマンドは `rtrb`、`Arc` は戻りキュー）と、デコーダーの置き場所は案 A（`ink-media`）。

## Why

- SE は短いので、全部持つと、再生が簡単で、CPU も小さい。測定では 60 秒の SE でも約 23 MB
- BGM を全部持つと、5 分で約 100〜110 MiB。曲を切り替えるたびに数百 ms のデコードが要る。ストリーミングなら、メモリは数 MiB で、CPU も実時間の約 0.1% で済む。測定で、ストリーミングは十分に軽いと分かった
- atomic とロックを使わないキューなら、音声スレッドが待つことも、メモリを確保することもない（ADR-0007 と同じ考え方）
- `Arc` を音声スレッドで落とすと、メモリの解放が音声スレッドで起きうる。戻りキューで制御側に返せば、解放は制御側で起きる。戻りキューの容量を「持てる数 + 運ばれている数」以上にし、未返却の数を制御側で数えれば、音声スレッドで満杯にならないことを、音声スレッドの動きに関係なく保証できる
- リサンプルは、ワーカーでの処理で、CPU も小さい（1 コアの約 0.1%）。SE を読み直す時間も短い。そのため、元のデータを持たず、ファイルから読み直せば、メモリが減って、作りも単純になる
- MP3 の gapless 情報があれば、symphonia が余分なフレームを取り除くので、隙間は 0。無いものだけ、十数 ms の隙間が出る。その違いは、使う人が見分けにくいので、「ループさせたい曲は WAV」と案内するのが確実
- `ink-media` に分ければ、MPL-2.0 の依存が 1 か所に閉じ、core のビルドとテストが軽いままになる（創作PC は RAM 8GB）

採用しなかった案:

- 全部デコードして持つ（BGM）：メモリが大きい
- SE もストリーミング：短い音に対して、ワーカーとのやり取りが増え、再生の始まりが遅れる
- `Arc` を音声スレッドで落とす：解放が音声スレッドで起きうる
- `Mutex` 付きのキュー：音声スレッドが UI のロックを待つ可能性がある（AGENTS.md §5）
- `ink-core` の module / `ink-assets`：上の表のとおり

この ADR の判断は一般的な考え方に基づくもので、法的な助言ではない。

## Consequences

- **合計が 0 dBFS を超えうる：** MIC + BGM + SE を足すと、合計がフルスケールを超えることがある。Limiter は Phase 3 なので、Phase 2 では、#40 の CLIP ランプで気づけるようにする
- **ループの既知の制限：** MP3 は、gapless 情報の無いファイルで、つなぎ目に十数 ms の隙間が出る。ループさせたい曲は WAV を推奨する。ARCHITECTURE.md §10 と README に書いた（#63）。F の UI にも書く。H の README は全体を見直す
- **#63 の制限と注意：** 末尾の「変更履歴」の「2026-10-19：#63（E）の実装で変えた点」にまとめた（計数アロケーターが見ていない範囲、破棄順序の前提、`take_error`、メモリ、順序 B、非ループの終端）
- **SE の読み込み中は鳴らせない：** セッションの作り直しのとき、SE をファイルから読み直す間は、その SE を鳴らせない。SE が多いときの時間は、E・F の実機で確かめる
- **新しい crate `ink-media`：** 依存は `ink-media → ink-core`。symphonia（MPL-2.0）が入るので、配布するときのライセンス表記が必要（Phase 2 の `cargo-about`、#66）
- **`load_sound` の一時的なメモリのピーク：** デコード結果、リサンプルの入力と出力、作業用のバッファが同時にあるので、ピークは最終的なサイズの約 3.3 倍になる（60 秒の SE で、最終 22 MB のところ 約 70 MB）。ワーカー側の処理で問題ないが、SE の合計上限（256 MB）を管理する D では、読み込み中のピークも考えに入れる。レートが 48000 と公約数が小さい音源（44101 Hz、22051 Hz など）でも、60 秒で 約 0.2 秒、ピーク 約 70 MB で、特別な対策は要らなかった（試作の実測）
- **symphonia 0.6 系は新しい：** API が変わりうるので、バージョンを固定し、更新は ADR か Issue で確かめる
- **MP3 の gapless 情報が無い場合の隙間は、補正しない：** 補正（先頭の無音を自分で取り除く）は、Phase 2 では入れない
- **Windows：** この ADR の測定は Linux（創作PC）。デコードとリサンプルは純粋な Rust なので、CI のビルドとテストで確かめ、実機の確認は #33 に追記する
- **ADR-0007 との関係：** 「Phase 1 ではコマンドのキューを使わない。値以外を送る必要が出たら（Phase 2 の SE の再生など）、そのときに決める」を、この ADR で決めた。Phase 1 の Graph・MIC・値の受け渡しは変えない
- **別の ADR が要るもの：** Phase 4 の「PC 内のアプリの音の取り込み」と、将来の「外部入力チャンネル」（別機器のクロックのずれの補正）は、作るときに別の ADR で決める
- **Asset ID の作り方、ライブラリの索引の形式、`SoundData` の細かい形：** C・B で決める

## 変更履歴

### 2026-10-19：#62（D）の実装で変えた点

実装の途中で、この ADR の「戻りキューが音声スレッドで満杯にならない」という保証を、**厳密に成り立たせる**ために、次の点を変えた（所長の承認を受けた）。Decision の該当箇所は上のとおり書き換えてある。

| 当初の ADR | 実装 | 理由 |
|---|---|---|
| コマンド：`SetSe` / `ClearSe` / `PlaySe { slot, gain, policy }` / `StopSe` / `StopAllSe`。置き場の表は音声側にある | コマンド：`PlaySe { slot, sound, gain, policy }`（`Arc` を運ぶ）/ `StopSe { slot }` / `StopAllSe`。置き場の表は制御側（`SeController`） | 音声側が自分で `Arc` を複製すると（`PlaySe` が参照を作る）、制御側は返ってくる数を事前に数えられない（再生が無視されたとき、返る数が合わなくなる）。`PlaySe` が `Arc` を運び、音声側が**必ず 1 つ返す**形にすれば、「運んだ数 − 受け取った数」が正確になる |
| ボイスは固定 16 | 同時に鳴らせるのは 16。フェードアウト中の分として 16 を足し、物理的には 32 | 「止めて頭から」と Stop で、プチ音が出ないようにするため（10 ms のフェードアウト） |
| 戻りキューの容量：置き場 + ボイス + コマンドキュー | 物理ボイス 32 + コマンドキュー 256 = 288。未返却が 288 に達したら `Busy` | 置き場の `Arc` は制御側にあり、戻りキューには来ない。戻りキューに入りうる `Arc` は、ボイスとコマンドキューの分だけ |
| 17 個目の同時再生（記載なし） | 新しい再生を捨てて数える（`Arc` は返す）。鳴っているボイスを奪わない | 奪うとプチ音が出る。パッドで 16 個の同時再生はふつう起きない |
| フェード枠が埋まったとき（記載なし） | フェードの残りが一番少ないフェード中のボイスを切って `Arc` を返す | 一番古いものは、ほぼ聞こえない。物理ボイスが 32 で固定のまま、空きボイスが必ずある、が崩れない |
| ストリームを閉じるとき（記載なし） | `SePlayer` の `Drop` が、ボイスとコマンドキューに残った `Arc` を戻りキューへ返す | バックエンド（cpal の ALSA・WASAPI）は、コールバックをワーカースレッドに持たせ、ストリームを閉じるときにそのスレッドで破棄する。返さないと、最後の参照がそこで落ち、解放が音声側のスレッドで起きる。GUI ではデバイスを切り替えるたびにセッションを作り直すので、再生中に閉じることは普通に起こる |
| SE の置き場の数（記載なし） | 64 | サウンドパッドの SE の数の目安。F で変えてよい |
| SE の合計の見積もり（記載なし） | `set_sound` が合計 256 MiB を超えるなら断る。読み込みは 1 本ずつ順に行う | 読み込み中のピーク（約 3.3 倍）を合計に数えないかわりに、同時に読まない |

その他、実装で決めたこと：

- 1 ブロックの最初に取るコマンドは最大 64 個。残りは次のブロックに回す（1 ブロックが長くならないように）
- 音声側で戻りキューに入れられなかったとき（保証が崩れたバグ）は、`mem::forget` して `leaked` に数える。テストでは 0 を確かめる
- `MicGraph::with_se` は、`SePlayer` の `max_frames` がグラフと同じでなければ、構築時に panic する（音声スレッドで panic させないため）
- SE の経路：`SePlayer` の合計 → SE の `GainNode`（音量）→ SE のメーター（ゲインの後、ミュートの前。MIC と同じ）→ ミュートの `GainNode` → `MixerNode`。SE を付けなければ、出力は Phase 1 と同じ（テストで一致を確かめた）

保証を確かめるテスト（`ink-core`）：容量の式、最悪のケース（`collect()` を一度も呼ばず、コマンドキューを 256 個の `PlaySe` で満杯にし、ボイスもすべて使う。戻りキューはちょうど 288 まで入り、`leaked` は 0、次の再生は `Busy`）、乱数の列で「送った数 = 受け取った数」、実スレッドの音声スレッド、フェード枠が埋まったときの切り捨て、ストリームを閉じるときの `Drop`、計数アロケーターで「`render` の間は確保 0・解放 0、解放は `collect()` で制御側」。

実測（#62、創作PC：Intel N100、release、Logi USB Headset、48 kHz。音が出ない設定 `--gain -60 --master -60` で、30 秒間の CPU）：

| 条件 | CPU（全体） | 備考 |
|---|---|---|
| `--se` 無し | 1.83%（出力スレッド 1.07%） | #38 の 2.0% と同程度 |
| 0.4 秒の SE を 0.5 秒ごと | 1.83%（出力スレッド 1.10%） | xrun 0、leaked 0 |
| 10 秒の SE を 0.05 秒ごと（20 回/秒） | 2.43%（出力スレッド 1.23%、メイン 0.43%） | dropped 760、leaked 0、xrun 0。メインが増えるのは、再生の時刻を合わせるため 12 ms ごとに確認するから |
| 44.1 kHz の SE を 1 秒ごと | 2.07% | `44100 Hz -> 48000 Hz`、読み込み 26〜30 ms |

所長の実機確認（SE を音を出して鳴らした場合）：20 秒・1 秒ごとで 20 回聞こえた（started 20、leaked 0、xrun 0）／10 秒の SE を 0.05 秒ごとで 16 の上限を超えても落ちず、プチ音なし（started 32、dropped 368、leaked 0、xrun 0）／48 kHz と 44.1 kHz の 440 Hz が同じ高さ／61 秒・音声でないファイル・存在しないファイルはエラーで終了コード 1／再生中に USB を抜くと約 3 秒でエラーで止まる（固まらない）。

### 2026-10-19：#63（E）の実装で変えた点

実装の途中で、BGM の音声スレッドの動きを、テストで確かめられる形に詰めた。Decision の該当箇所は上のとおり書き換えてある。

| 当初の ADR | 実装 | 理由 |
|---|---|---|
| リングバッファは 1 秒分 | 1 秒分と「ブロックの 4 倍」の大きい方。製品のブロック（4096）では 1 秒 | 小さなレートや長いブロックでも、始まりの量にブロック 1 つが入るため |
| 世代番号の手順（`stopped` と `drained`） | 手順に加えて、**曲の終わりの印 `eof`（世代 + 1）**と `finished` | 曲の終わりと Stop が競合しても、古い終わりの印が新しい曲に効かないため |
| 足りないとき：無音を出して数える | **フェードアウト → 無音 → priming で戻る。** 数えるのは中断の回数と無音のフレーム数 | 急な無音はプチ音になる。残りの「ブロック + フェード」分でフェードアウトする |
| 始まりの量（記載なし） | priming：`max(100 ms, ブロック + フェード)`。`eof` が立っていれば貯まった分で始める | 始まってすぐに足りなくなるのを防ぐ。短い曲が待ち続けないようにする |
| Pause・Stop は MIC と同じ 10 ms のスムージング | サンプル単位の 10 ms の直線ランプ。フェードアウトの間に読んだ分は、再開時に飛ばす。フェードを途中で切った場合は 0 から始め直す | ブロックの境目に依存しない。切った後に 1 から飛ばない |
| Loop：ワーカーが先頭へシークして続ける | 加えて、**1 周の出力フレーム数を毎周同じにし、先頭でならす（1.5 ms、案 B）** | リサンプラーの遅れが隙間にならない。段差のクリックを減らす（タグの無い MP3 の隙間は補正しない） |
| リサンプル：1024 フレームのチャンク | `StreamResampler`：遅れを数えて取り除き、終わりを押し出す。一括版とビット単位で一致 | Loop で `reset` した後も同じ長さと先頭になる |
| ワーカー（記載なし） | `ink-bgm` スレッド。chunk は 2048 フレーム。待ちは 2 ms と 5 ms。終わるのは `BgmWorker` の破棄だけ | 破棄が数 ms で返る。エラーや曲の終わりで止まらない |
| 失敗の扱い（記載なし） | 曲を終わらせる（`begin_stream(Some(0))` と `mark_eof`）。`BgmFailure` を記録し、最初の失敗は取り出されるまで残る。次の Stop で開き直す | プレイヤーが priming で待ち続けない。一時的な失敗から戻れる |
| 破棄の順序（記載なし） | `Bgm` は、ワーカーを join してからコントローラー。`AudioSession` は `input`、`output`、`se`、`bgm` の順 | リングバッファの解放を制御側で起こす |
| `run` の引数：`--bgm`、`--bgm-loop`、`--bgm-volume` | 加えて `--bgm-cycle`（実機確認用）。`--bgm-volume` は範囲外をエラーにする | Pause・Stop・再生のくり返しを、窓の前に実機で確かめる |

その他、実装で決めたこと：

- `MicGraph::with_bgm`：プレイヤーの `max_frames` がグラフと同じでなければ、構築時に panic する（音声スレッドで panic させないため）
- グラフの経路：BGM の `BgmPlayer` → BGM の `GainNode`（音量）→ BGM のメーター（ゲインの後、ミュートの前）→ ミュートの `GainNode` → `MixerNode`。ミキサーの入力は [MIC, BGM, SE]。BGM を付けなければ、出力は Phase 1 と同じ（テストで一致を確かめた）
- `AudioSession` は `SessionOptions { bgm }` で BGM を付ける。付けなければ、リングバッファもプレイヤーもスレッドも作らない（GUI は今は付けない）
- `try_open` は、ストリームを開く**前**に `Bgm::start` を呼ぶ。失敗したら、すぐセッション全体の失敗にする

保証を確かめるテスト：計数アロケーター（`ink-core/tests/realtime_alloc.rs`）で、普通の再生、Pause のフェード、アンダランのフェードと priming、Stop、曲の終わり、フェードを途中で切る経路のどれでも、`render` の間の確保・解放が 0 であること（わざと壊すと失敗することも確かめた）。破棄の順序 A・B・C。リングバッファの世代の受け渡しと `eof` のテスト。ワーカーを 1 周ずつ動かすテストと、実スレッドのテスト（Stop が古い chunk の端数を混ぜない、曲の切り替え、`load` と `request_flush` の順序、失敗した曲が `finished` になる、古い `eof` が新しい曲に効かない、`Bgm` の破棄が 1 秒以内に返る）。リサンプルの周ごとの長さ。

#### 制限と注意

1. **計数アロケーターのテストは、ストリームを閉じるときの経路を見ていない。** 確かめたのは、`render` の間の確保・解放が 0 であることと、プレイヤーとコントローラーの破棄順序ごとの解放のスレッドである。`MicGraph` が持つ固定のバッファ（`AudioBuffer` など）を、ストリームを閉じるときにどのスレッドで解放するかは、まだ見ていない。今回は見送り、[#72](https://github.com/InkInc-official/ink-mixer/issues/72) に切り出した
2. **`try_open` で `Bgm::start` をストリームを開く前に呼ぶ位置が、リングバッファの解放順序の前提である。** 失敗したときも、ストリームが先、`Bgm` が後に落ちる。位置を動かすときは、破棄順序のテストと合わせて見直す
3. **`Bgm::take_error` を読まない呼び出し側では、BGM の失敗が見えない。** ワーカーのログは `debug!` なので、`RUST_LOG=debug` でしか出ない。`run` は取り出して標準エラーに 1 行出す。GUI（F）は、取り出して画面に出すこと
4. **常駐メモリの最悪は約 17 MiB ＋ アートの大きさ。** 内訳：リングバッファ 0.35〜0.77 MiB（44.1〜96 kHz）、リサンプラー（通常のレートで 40〜140 KiB、公約数の小さいレートで約 5 MiB、最悪で約 13 MiB）、プレイヤーとグラフのバッファと chunk 用のベクタで 1 MiB 未満。通常のレートでは約 2 MiB 以下。アルバムアート付きの MP3 は、アートの約 1 倍が曲を開いている間ずっと常駐し、**`open` の瞬間のピークはアートの約 2 倍**になる（3.2 MB のアートで、常駐 +3 MB、ピーク +6 MB を実測。symphonia の `limit_visual_bytes` を 0 にしても減らなかった）。SE の合計上限 256 MiB と合わせて、RAM 8GB の創作PC に収まる
5. **コントローラーを先に落とす順序 B は制限である。** プレイヤーを落としたスレッドで、リングバッファの解放が 1 回起きる。`Bgm` の構造では順序 A（制御側で解放）になるので、通常は起きない。テストに記録してある
6. **非ループの終端でプチ音が出た場合の選択肢**（所長が実機で聴いて、出たときだけ実装する。2026-10-29 の実機では、プチ音は聞こえなかったので、実装していない）：
   - **案 1（音声側）：** 曲の終わりの印（`eof`）が立っていて、残りのフレームが「フェードの長さ（10 ms）」になったところから、最後のフレームまでを 1 → 0 に下げる。**新しい状態は要らない：** 足りないときのフェードアウト（`FadingOut`）がそのまま使える。足すのは、フェードの後に「曲が終わった」へ進む行き先（`After` の値 1 つ）と、開始の位置合わせだけである。ブロックの途中から下げ始める必要があるので、ブロックを 2 つに分けて、後ろの部分の前に `GainNode` の目標を 0 にする。分けずにブロックの先頭で始めると、最大 1 ブロック（デバイスのコールバック。ふつう数 ms〜20 ms、最大 4096 フレーム）早く下がり始め、曲の最後がその分、無音になる。音声側は残りのフレーム数を正確に知っているので、ちょうどの位置で下げられる
   - **案 2（ワーカー側）：** 最後の chunk の末尾に下げを掛ける。音声スレッドは変えなくてよいが、最後の chunk がフェードの長さより短いと、その前の chunk はもうリングバッファに書き込み済みで、下げられない。末尾のフェード分を手元に残してから書く作りが要る
   - 継ぎ目のならし（案 B）は始まりに掛けるもので、終端にはそのままでは使えない
7. そのほか：BGM に `leaked` に当たるものは無い（音声スレッドに `Arc` を渡さない）。タグの無い MP3 の隙間は補正しない。Stop の直後の数十 ms だけ、状態の行が `finished` のままに見えることがある（フラッシュを音声スレッドが処理するまで）。曲が終わった旨の行は二重に出ない
